# 🤖 بوت استضافة بوتات تيليجرام (Telegram Bot Hosting)

بوت تيليجرام رئيسي يعمل كمنصة استضافة لبوتات تيليجرام أخرى: يستقبل ملفات
بايثون أو أرشيفات مضغوطة تحتوي بوتات، ويشغّلها كعمليات منفصلة مع بيئة
افتراضية خاصة بكل بوت، ويوفر تحكمًا كاملًا من داخل تيليجرام.

## ✨ المزايا

- رفع بوت بملف `.py` واحد أو أرشيف `.zip` كامل (مع `requirements.txt`)
- بيئة بايثون افتراضية (venv) معزولة لكل بوت + تثبيت تلقائي للمتطلبات
- تشغيل / إيقاف / إعادة تشغيل بضغطة زر
- **حارس تلقائي (Watchdog)**: يكتشف توقف أي بوت بشكل مفاجئ ويعيد تشغيله
  تلقائيًا، ويرسل إشعارًا فوريًا لصاحبه
- عرض السجلات (Logs) الحية لكل بوت
- مراقبة استهلاك المعالج والذاكرة ومدة التشغيل لكل بوت
- إدارة متغيرات بيئة (Environment Variables) لكل بوت — مثال: توكن البوت
  الفرعي نفسه، بدون كتابته داخل الكود
- نظام مستخدمين متعدد: كل مستخدم يرى ويدير بوتاته فقط، بحد أقصى قابل للتعديل
- لوحة تحكم للمشرفين: إحصائيات عامة، إدارة المستخدمين (حظر/فك حظر/تعديل
  الحد الأقصى)، عرض كل البوتات، إرسال رسالة جماعية (Broadcast)
- استعادة تلقائية للبوتات التي كانت تعمل عند إعادة تشغيل السيرفر

## 📦 التثبيت

```bash
pip install -r requirements.txt
```

يتطلب بايثون 3.9 فأكثر (لإمكانية إنشاء بيئات افتراضية للبوتات المستضافة عبر
وحدة `venv`).

## ⚙️ الإعداد

اضبط متغيرات البيئة التالية قبل التشغيل (أو عدّلها مباشرة في `config.py`):

| المتغير         | الوصف                                              |
|------------------|-----------------------------------------------------|
| `HOST_BOT_TOKEN` | توكن بوت الاستضافة الرئيسي (من [@BotFather](https://t.me/BotFather)) |
| `ADMIN_IDS`      | آيديات المشرفين مفصولة بفاصلة، مثل `111,222`        |

على لينكس/ماك:

```bash
export HOST_BOT_TOKEN="123456:ABC-your-token"
export ADMIN_IDS="111111111,222222222"
```

## ▶️ التشغيل

```bash
python main.py
```

سيبدأ البوت بالعمل، ويستعيد تلقائيًا تشغيل أي بوتات كانت شغّالة قبل الإغلاق.

يُفضّل تشغيله داخل `screen` أو `tmux` أو كخدمة `systemd` أو عبر `pm2` حتى يبقى
يعمل باستمرار على السيرفر.

```

├── requirements.txt
├── example_hosted_bot/     # مثال لبوت جاهز لتجربة الرفع والاستضافة
│   ├── main.py
│   └── requirements.txt
└── uploaded_bots/          # يُنشأ تلقائيًا، يحتوي ملفات بوتات المستخدمين
```

## 📝 ملاحظات مهمة لأصحاب البوتات المستضافة

- يجب أن يقرأ البوت المرفوع توكنه الخاص من متغيرات البيئة، مثل:
  ```python
  import os
  TOKEN = os.environ["BOT_TOKEN"]
  ```
  ثم يُضاف `BOT_TOKEN` كمتغير بيئة من لوحة تحكم البوت (⚙️ متغيرات البيئة).
- إن كان مشروعك متعدد الملفات، ارفعه كأرشيف `.zip` يحتوي كل الملفات، وضع
  فيه `requirements.txt` إن احتجت مكتبات إضافية غير مثبّتة افتراضيًا.
- يبحث النظام تلقائيًا عن ملف التشغيل الرئيسي بالترتيب: `main.py`، `bot.py`،
  `app.py`، `run.py`، `start.py`، وإلا يستخدم أول ملف `.py` يجده.

## 🔒 تنبيه أمني

هذا المشروع يُشغّل أكواد بايثون يرفعها المستخدمون كعمليات منفصلة على نفس
الجهاز. إن كنت ستفتح الخدمة لمستخدمين لا تثق بهم، يُنصح بشدة بتشغيل المشروع
داخل حاوية (Docker) أو خادم افتراضي معزول (VM/Sandbox)، وتقييد صلاحيات
النظام والشبكة، لمنع أي كود ضار من التأثير على السيرفر أو بقية البوتات.

## 🔒 تحديثات أمان وموثوقية (تم تطبيقها)

هذه النسخة تتضمن الإصلاحات التالية مقارنة بالنسخة الأصلية:

1. **إصلاح ثغرة Zip Slip** (`utils.py::extract_zip`) — التحقق من كل مسار داخل الأرشيف قبل الاستخراج لمنع الكتابة خارج مجلد البوت.
2. **حماية من Zip Bomb** — حد أقصى قابل للضبط لحجم الملفات بعد فك الضغط (`MAX_EXTRACTED_SIZE_MB` في `config.py`).
3. **تعقيم اسم البوت (HTML escape)** قبل عرضه — كان يمكن حقن وسوم HTML/روابط عبر اسم البوت.
4. **تعقيم نص البث الجماعي (Broadcast)** + معالجة حد الإرسال (Flood Control) من تيليجرام.
5. **حماية من حلقة التعطل (Crash Loop)** — تعطيل تلقائي لإعادة التشغيل بعد عدد محاولات متتالية (`MAX_AUTO_RESTART_ATTEMPTS`) مع تأخير تصاعدي (Exponential Backoff)، دون حجب مراقبة بقية البوتات.
6. **حدود موارد لكل بوت مستضاف** (RAM/CPU عبر `resource.setrlimit` على Linux) — `MAX_BOT_MEMORY_MB` و `MAX_BOT_CPU_SECONDS`.
7. **تفعيل WAL mode لقاعدة SQLite** لتحسين الأداء تحت التزامن.
8. **تخطي إعادة تثبيت `requirements.txt`** إن لم يتغيّر محتواه (بمقارنة hash)، مع مهلة زمنية (`timeout`) لكل أوامر pip/venv.
9. **رفض التشغيل بدون `HOST_BOT_TOKEN`** بدل قيمة افتراضية وهمية.
10. **إصلاح ثغرة Path Traversal عند رفع ملف `.py` مباشر** (`main.py::new_bot_file`) — اسم الملف قادم بالكامل من المستخدم عبر تيليجرام، فأصبح يُعقَّم عبر `utils.safe_filename()` (اسم الملف فقط، ورفض أي `..` متبقٍّ) بدل استخدامه كما هو في مسار الحفظ.
11. **معالج إغلاق نظيف (SIGTERM/SIGINT)** يستدعي `pm.shutdown_all()` قبل الخروج، مع تحقق `psutil.pid_exists()` في `restore_running_bots()` قبل إعادة تشغيل أي بوت مسجَّل "running" لتفادي تشغيل نسخة ثانية فوق عملية يتيمة لا تزال حيّة. كما تعمل العمليات الفرعية الآن في جلسة مستقلة (`start_new_session=True`) حتى لا ترث إشارات إنهاء الخادم الرئيسي.
12. **تدوير ملفات السجل (Log Rotation)** — اقتطاع تلقائي لـ `run.log` عند تجاوزه `MAX_LOG_SIZE_MB` (الاحتفاظ بآخر نصف الحجم المسموح بدل حذفه بالكامل أو تركه ينمو بلا حدود).
13. **تصفية متغيرات البيئة الحساسة** — قائمة `PROTECTED_ENV_KEYS` (`PATH`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `PYTHONHOME`, `PYTHONPATH`, `PYTHONSTARTUP`) تُفرض دائمًا من بيئة الخادم عند تشغيل أي بوت مستضاف، ولا يمكن للمستخدم تعيينها كمتغيرات بيئة لبوته.
14. **رفع الحد الافتراضي للذاكرة** إلى 1024MB (كان 512MB يقيّد مساحة العناوين الافتراضية لا الاستخدام الفعلي)، مع إمكانية تخصيص حد ذاكرة مستقل لكل بوت (عمود `max_memory_mb`) وزرّي ➕/➖ في لوحة تحكم البوت.
15. **منع "البوتات الشبح"** — تأجيل إنشاء صف البوت في قاعدة البيانات حتى ينجح استخراج/تأكيد الملف فعليًا، بدل إنشائه فور إدخال الاسم (يحتفظ بالاسم مؤقتًا في الذاكرة حتى اكتمال الرفع).
16. **إعادة محاولة فعلية بعد Flood Control في البث الجماعي** — بعد الانتظار المطلوب من تيليجرام (429)، تُعاد محاولة الإرسال فعليًا مرة واحدة إضافية بدل احتساب الإرسال "فاشلًا" مباشرة.
17. **تبريد (Rate Limiting) على رفع بوت جديد** — حد أدنى `UPLOAD_COOLDOWN_SECONDS` بين محاولات بدء رفع بوت جديد متتالية لنفس المستخدم.
18. **ترتيب حتمي عند اختيار ملف التشغيل** — فرز أبجدي لملفات `.py` قبل اختيار الأول منها عند عدم وجود اسم مفضّل.
19. **التحقق من صحة مفتاح متغير البيئة** — رفض أي مفتاح لا يطابق صيغة اسم متغير بيئة POSIX صالحة.

⚠️ ملاحظة مهمة تبقى قائمة: البوتات المستضافة لا تزال تعمل كعمليات فرعية بنفس صلاحيات السيرفر (بدون عزل حاويات/Docker). للاستخدام في بيئة إنتاج حقيقية مع مستخدمين غير موثوقين، يُنصح بشدة بتشغيل كل بوت داخل حاوية Docker أو بيئة معزولة منفصلة.

## 🆕 تحديثات v3 (أمان وموثوقية إضافية + مزايا جديدة)

**إصلاحات أمنية/موثوقية:**

1. **إصلاح تسريب مسار في اسم ملف السجل المُرسَل** — اسم البوت (نص حر يدخله
   المستخدم) كان يُستخدم مباشرة كجزء من مسار كتابة على القرص عند إرسال سجل
   طويل كملف؛ الآن يُعقَّم عبر `safe_display_filename()` ويُكتب الملف الفعلي
   دائمًا باسم مؤقت عشوائي (`uuid`) على القرص، بينما الاسم المعروض للمستخدم
   يبقى الاسم المعقَّم.
2. **إصلاح حالة تسابق (Race/TOCTOU) عند إنشاء بوت جديد** — التحقق من الحد
   الأقصى والإدراج في قاعدة البيانات أصبحا عملية ذرّية واحدة
   (`insert_bot_if_room`) بدل استدعاءين منفصلين قابلين للتزامن.
3. **حد أقصى لعدد الملفات داخل أرشيف مرفوع** (`MAX_ZIP_FILE_COUNT`) — حماية
   إضافية من Zip Bomb عبر ملايين الملفات الصغيرة، بجانب حد الحجم الموجود مسبقًا.
4. **Semaphore عالمي على عمليات تجهيز venv/pip install** — يحدّ عدد هذه
   العمليات الثقيلة المتزامنة على مستوى السيرفر كله (`MAX_CONCURRENT_VENV_SETUPS`).
5. **تنظيف دوري لحالات المحادثة المعلّقة** (`pending`) وذاكرة التبريد
   (`_last_upload_at`) — تمنع تسرّب الذاكرة التدريجي من مستخدمين بدأوا محادثة
   ولم يكملوها.
6. **أمر `/cancel`** للخروج من أي محادثة معلّقة في أي وقت.
7. **البث الجماعي يستثني المستخدمين المحظورين** تلقائيًا.
8. **سجل تدقيق للأدمن (Audit Log)** — يسجّل إجراءات الحظر/فك الحظر/تعديل حدود
   البوتات/البث الجماعي مع الوقت ومن قام بها.

**مزايا جديدة:**

9. **🔄 تحديث كود بوت موجود** دون حذفه — يستبدل الملفات فقط ويحافظ على
   `bot_id`، متغيرات البيئة، وسجل التشغيل. يتضمن فحص صياغة سريع (syntax
   check) للكود الجديد قبل إعادة التشغيل، والكود القديم يبقى سليمًا إذا فشل
   الاستخراج أو لم يُعثر على ملف تشغيل صالح.
10. **✅ فحص صياغة بايثون (Syntax Check)** تلقائي عند أول رفع وعند كل تشغيل
    يدوي — يُظهر أخطاء صياغية للمستخدم فورًا بدل انتظار Crash بعد التشغيل.
11. **🩺 فحص صحي حقيقي (Health Check)** — إن عرّف صاحب البوت متغير بيئة باسم
    `BOT_TOKEN` (توكن بوته الفرعي)، يستدعي النظام `getMe` دوريًا للتأكد أن
    البوت متصل فعليًا بتيليجرام، وليس فقط أن عمليته حيّة على مستوى النظام.
12. **⏰ إعادة تشغيل دورية مجدولة اختيارية** لكل بوت (كل 6/12/24/48 ساعة أو
    معطّلة) — مفيدة لبوتات تحتاج تنظيف دوري لحالتها الداخلية.
13. **📈 سجل استخدام تاريخي** (Sparkline) لاستهلاك CPU/RAM لكل بوت على مدار
    آخر عدة لقطات، بدل رقم لحظي واحد فقط.
14. **📁 تنزيل ملفات البوت** كأرشيف zip كامل في أي وقت (نسخة احتياطية شخصية).
15. **📤/📥 تصدير واستيراد متغيرات البيئة** كملف `.env` قياسي.
16. **فلترة قائمة البوتات للأدمن** حسب الحالة (شغّالة فقط / متعطلة فقط).

## 🐳 تحديثات v4 — تجهيز التشغيل 24 ساعة والنشر على JustRunMy.App

هذه الدفعة لا تضيف مزايا مستخدم جديدة، بل تُحصِّن استمرارية عمل **بوت
الاستضافة نفسه** (وليس البوتات المستضافة بداخله، التي كانت محمية أصلًا عبر
Watchdog) وتُجهّزه للنشر كحاوية Docker جاهزة:

1. **حلقة حماية خارجية حول `infinity_polling`** — مكتبة `pyTelegramBotAPI`
   تعيد المحاولة داخليًا عند أخطاء الشبكة المؤقتة، لكن لو حدث استثناء غير
   متوقع أوقف الحلقة بالكامل، أصبح البرنامج يعيد تشغيلها فورًا بعد 5 ثوانٍ
   بدل الخروج والانتظار حتى تكتشف المنصة توقف الحاوية وتعيد تشغيلها من
   الصفر (وهو أبطأ وأثقل، لأنه يعني إعادة تشغيل كل البوتات المستضافة أيضًا
   عبر `restore_running_bots`).
2. **خادم فحص صحة HTTP اختياري** (`_start_health_server` في `main.py`) —
   يعمل فقط إن عرَّفت لوحة المنصة متغير بيئة `PORT`؛ وضع Polling الافتراضي
   لا يحتاجه إطلاقًا ولا يتأثر بغيابه.
3. **`Dockerfile`** جاهز: صورة `python:3.11-slim`، مخرجات غير مخزَّنة
   مؤقتًا (`PYTHONUNBUFFERED=1`) حتى تظهر السجلات فورًا في لوحة "Logs"،
   تثبيت `build-essential` لدعم تجميع حزم بايثون التي تحتاجها بعض البوتات
   المستضافة، مستخدم غير جذر (`appuser`)، وصيغة `CMD` من نوع exec حتى تصل
   إشارة `SIGTERM` مباشرة لعملية بايثون فيُنفَّذ الإغلاق النظيف الموجود
   أصلًا (إيقاف كل البوتات المستضافة بأمان قبل توقف الحاوية).
4. **`.dockerignore`** — يمنع تسرّب `uploaded_bots/` و`hosting.db` وملفات
   السجلات المحلية إلى داخل صورة Docker نفسها؛ هذه يجب أن تعيش على قرص دائم
   توفره المنصة، لا داخل صورة تُعاد بناؤها عند كل نشر.
5. **`.env.example`** — قائمة متغيرات البيئة المطلوبة لنسخها إلى لوحة تحكم
   المنصة مباشرة.

### 🚀 خطوات النشر على JustRunMy.App

> JustRunMy.App منصة استضافة حاويات (Container Hosting) تدعم Telegram bot
> hosting تحديدًا، مع تشغيل دائم 24/7 وإعادة تشغيل تلقائية عند الأعطال. وضع
> Polling (المستخدم هنا افتراضيًا) يعمل عندهم "جاهزًا بدون إعداد" دون حاجة
> لفتح أي منفذ.

1. اضغط كل محتويات المشروع (بما فيها `Dockerfile`) في ملف `.zip` واحد، **أو**
   اربط المستودع عبر Git إن كان الكود على GitHub/GitLab.
2. من لوحة JustRunMy.App: أنشئ تطبيقًا جديدًا واختر طريقة النشر **Zip
   Upload** (ارفع الملف المضغوط) أو **Git Push**. بما أن المشروع يحتوي
   `Dockerfile` جاهزًا، ستُستخدَم صورته مباشرة بدل الاكتشاف التلقائي.
3. من قسم **Environment Variables** في لوحة التطبيق، أضف (راجع
   `.env.example`):
   - `HOST_BOT_TOKEN` = توكن بوت الاستضافة من BotFather
   - `ADMIN_IDS` = آيديات المشرفين مفصولة بفاصلة
4. **لا حاجة لإضافة/فتح أي منفذ (Port)** ما دام البوت يعمل بوضع Polling
   الافتراضي — اترك هذا الجزء فارغًا في اللوحة.
5. فعّل خيار **Persistent Disk / Storage** إن كان متاحًا وثبّته على مجلد
   المشروع (`/app`)، حتى تبقى قاعدة البيانات (`hosting.db`) وملفات البوتات
   المرفوعة (`uploaded_bots/`) محفوظة بين عمليات إعادة النشر (Redeploy)، لا
   فقط بين إعادة التشغيل العادية (Restart) — بعض المنصات تحتفظ بالقرص بين
   الحالتين افتراضيًا، فتحقق من إعدادات تطبيقك تحديدًا.
6. اضغط **Start**. راقب تبويب **Logs** — يجب أن تظهر رسالة
   `✅ البوت يعمل الآن.` خلال ثوانٍ. من هذه اللحظة، البوت الرئيسي يعمل
   بشكل دائم 24/7، والحارس الداخلي (Watchdog) يراقب أي بوت مستضاف بداخله
   ويعيد تشغيله تلقائيًا عند الانهيار، بينما تتكفّل المنصة نفسها بإعادة
   تشغيل الحاوية كاملة في الحالات النادرة جدًا التي قد يتعطل فيها البرنامج
   الرئيسي نفسه بالكامل.

**ملاحظتان مهمتان لم تُنفَّذا بعد عمدًا (نطاقهما أكبر من تعديل كود):**

- **العزل الحقيقي عبر Docker/حاويات** — لا يزال البوتات المستضافة تعمل
  كعمليات فرعية بصلاحيات السيرفر نفسه؛ العزل الكامل يتطلب Docker مثبَّتًا على
  الخادم وإعادة هيكلة طبقة التشغيل بالكامل (مشروع منفصل).
- **دعم لغة إنجليزية كاملة (i18n)** — يتطلب ترجمة كل النصوص المعروضة للمستخدم
  (~900 سطر) وآلية اختيار لغة لكل مستخدم؛ لم يُنفَّذ في هذه الدفعة.


## 🚂 النشر على Railway

المشروع يحتوي على `Dockerfile` و`railway.json` جاهزين للبناء والنشر على Railway. بعد ربط مستودع GitHub بالمشروع، أضف متغيري البيئة `HOST_BOT_TOKEN` و`ADMIN_IDS` من لوحة Railway، ولا تضع أي قيم حقيقية داخل المستودع.

للحفاظ على قاعدة البيانات وملفات البوتات المرفوعة بين عمليات إعادة البناء، أنشئ **Volume** للخدمة على Railway واجعل مسار التركيب `/app/data`، واترك كود التطبيق في `/app`. يضبط Dockerfile تلقائيًا المتغير `DATA_DIR=/app/data`، ويضبط سكربت بدء التشغيل ملكية المجلد ثم يشغّل التطبيق كمستخدم غير جذر؛ لذلك لا تحتاج إلى إضافة `RAILWAY_RUN_UID`. يستخدم التطبيق المنفذ الذي توفره Railway عبر المتغير `PORT` ويعرض نقطة فحص على المسار `/`.

> تنبيه: هذا المشروع يشغّل كود Python يرفعه المستخدمون كعمليات فرعية داخل نفس الحاوية. لا تفتح المستودع أو الخدمة لمستخدمين غير موثوقين في بيئة إنتاجية دون عزل أقوى، مثل حاوية مستقلة لكل بوت أو خادم منفصل.
